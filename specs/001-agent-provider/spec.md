# Feature Specification: Agent Provider(大模型统一对接前台)

**Feature Branch**: `016-lesson16-provider`

**Created**: 2026-08-16

**Status**: Draft

**Input**: User description: "第16节需求:Agent Provider——Agent 与大模型之间的统一对接前台。Provider 是 Agent 与大模型之间的前台:上层递入一份 Profile(配置)和一段 Prompt(内容),Provider 挑对模型、按对方协议发出、原样拿回回话;换模型只改配置。"

## Clarifications

### Session 2026-08-16

- Q: 环境变量占位符指向的变量未设置时,如何处理? → A: 启动/加载期即报错——建立该供应商的模型客户端时校验凭证非空,缺失则报「供应商 X 凭证缺失(期望环境变量 Y)」;不阻断其余供应商,不等到调用期才以 401 暴露

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多供应商按名路由调用 (Priority: P1)

运维在同一实例上配置了多个大模型供应商(如 DeepSeek、Kimi),每个 Agent 通过自己的 Profile 声明用哪一家、哪个模型、什么温度。Agent 运行时每转一圈决策循环,系统按 Profile 里的供应商名字把请求准确路由到对应模型,多家并存互不串台。

**Why this priority**: 这是 Provider 的存在意义——没有它,上层要自己操心"这次调哪家、协议长什么样";路由串台等于把话发给了错的模型,是正确性底线。

**Independent Test**: 配置两个供应商,用指向第二家的 Profile 发起一次调用,验证命中的是第二家、第一家全程未被触碰。

**Acceptance Scenarios**:

1. **Given** 全局层声明了 deepseek 与 kimi 两个供应商,**When** 用 provider 名为 kimi 的 Profile 发起调用,**Then** 请求发给 kimi 对应模型,deepseek 对应模型零调用。
2. **Given** Profile 引用的供应商名在全局层不存在,**When** 发起调用,**Then** 系统直接报错指明该供应商名未注册,不悄悄用错或留空跑过。

---

### User Story 2 - Profile 批量加载与合法性校验 (Priority: P2)

运维在工作区的 `profiles/` 目录下放多份 Agent 配置文件(每份描述一个 Agent 的身份、供应商、模型、工具等完整字段)。系统启动时批量解析全部文件,建好按名查找的内存索引;单份文件写错了(语法坏、引用不存在的供应商)只记错误日志,不阻断其余文件加载;文件里的敏感值(如 API key)用环境变量占位符书写,加载时从环境变量解析出真值。

**Why this priority**: Profile 是"Agent 是配置出来的"这条项目底线的载体;Provider 是第一个消费 Profile 的模块,加载解析不牢靠,后面所有能力都建在沙子上。

**Independent Test**: 准备一份合法全字段文件、一份语法损坏文件、一份引用未知供应商的文件同目录加载,验证合法文件全字段可用、坏文件被跳过且有错误日志、引用未知供应商给出清晰报错。

**Acceptance Scenarios**:

1. **Given** 一份覆盖全部约定字段的合法 Profile 文件,**When** 系统加载,**Then** 所有字段解析完整、可按名查到。
2. **Given** 目录下混有一份语法损坏的文件,**When** 系统加载,**Then** 该文件记错误日志并跳过,其余文件正常加载。
3. **Given** 配置值写成 `${SOME_ENV_VAR}` 占位,**When** 环境变量已设置,**Then** 加载后读到的是环境变量的真值,占位符本身不出现在运行值里。

---

### User Story 3 - 工具说明随调用下发但绝不执行 (Priority: P2)

Agent 发起大模型调用时,需要把"本次可用工具清单及参数说明"一并带给模型,模型据此可能回答"我想调某个工具"。系统只负责把工具说明翻译成模型看得懂的格式随请求发出;模型返回的工具调用意图原样交回上层,Provider 自身绝不执行任何工具。

**Why this priority**: 底层框架自带"自动帮你执行工具"的机制,若不显式关闭,工具会被调两次且绕过上层沙箱管控——这是课程点名的头号坑,必须有回归测试永久钉死。

**Independent Test**: 带一个工具说明发起调用,检查发出的请求里工具说明已翻译携带、且自动执行开关处于关闭态;全程无任何工具被真实执行。

**Acceptance Scenarios**:

1. **Given** 一次携带可用工具清单的调用,**When** 请求发出,**Then** 请求内包含翻译后的工具说明且字段与源定义一一对齐。
2. **Given** 同上调用,**When** 检查请求配置,**Then** 底层框架的自动工具执行处于关闭状态。

---

### User Story 4 - 调用无论成败都留审计痕迹 (Priority: P3)

每次大模型调用——无论成功还是失败(超时、限流、模型报错)——系统都写入一条审计记录:供应商、模型、token 用量、耗时、成功标识、失败原因。失败时异常继续抛给上层处理,但审计先落账。

**Why this priority**: "可审计"是产品差异化卖点,失败调用不留痕等于真实事故在系统里完全隐形;审计表是 day one 就要立的地基。

**Independent Test**: 分别制造一次成功调用与一次失败调用,验证审计存储各多出一条记录,失败记录含成功标识=false 与失败原因,且失败调用的异常仍向上抛出。

**Acceptance Scenarios**:

1. **Given** 一次成功调用,**When** 调用返回,**Then** 审计记录含供应商、模型、token 用量、耗时、成功标识=true。
2. **Given** 一次因超时失败的调用,**When** 异常上抛,**Then** 审计记录含成功标识=false 与失败原因,且记录先于异常落地。

---

### Edge Cases

- Profile 引用的供应商名在全局层不存在:加载校验即报错,调用时再次兜底报错,两层都不放行。
- 供应商列表为空或未配置:系统可正常启动,任何调用尝试报"供应商未注册"。
- 环境变量占位符指向的变量未设置:建立该供应商的模型客户端时即校验凭证非空,缺失则报「供应商 X 凭证缺失(期望环境变量 Y)」的清晰错误;不阻断其余供应商的注册与启动,不留到调用期以 401 暴露。
- 审计写入自身失败(如存储不可用):不阻断调用主流程,记错误日志。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持声明多个大模型供应商,每个供应商有唯一名字,运行时按名字显式路由到对应模型;禁止靠扫描容器类型猜测供应商身份。
- **FR-002**: 每个 Agent 的 Profile MUST 能声明供应商名、模型名、温度;Profile 引用的供应商名在全局层找不到时 MUST 报错。
- **FR-003**: 系统 MUST 在启动时从工作区 profiles 目录批量加载全部 Profile 文件,完成全字段解析与合法性校验,并提供按名查找;单份坏文件 MUST 记错误日志且不阻断其余加载。
- **FR-004**: Profile 与全局配置中的敏感值 MUST 支持 `${ENV_VAR}` 占位符书写,加载时从环境变量解析;任何文件 MUST NOT 出现明文密钥。供应商凭证对应的环境变量缺失时,MUST 在建立该供应商客户端时报指明供应商名与变量名的错误,MUST NOT 留到调用期才暴露。
- **FR-005**: 发起大模型调用时 MUST 支持附带本次可用工具的参数说明(schema),且只做格式翻译,工具执行权 MUST NOT 在 Provider 内。
- **FR-006**: 系统 MUST 显式关闭底层框架的自动工具执行机制。
- **FR-007**: 每次大模型调用无论成败 MUST 写入审计记录,字段含:供应商、模型、prompt/completion/total token 用量、耗时、成功标识、失败原因、起止时间;审计表 MUST 由手工维护的建表脚本创建(含成功标识与失败原因两列),不依赖 ORM 自动迁移。
- **FR-008**: 供应商调用失败时 MUST 直接把错误抛给上层,MUST NOT 做自动切换、并发抢答或熔断。
- **FR-009**: 模型返回的工具调用意图 MUST 原样随响应交回上层,Provider MUST NOT 执行。

### Key Entities

- **供应商(Provider)声明**:全局层配置项,含唯一名字、凭证来源(环境变量占位)、可选的服务地址;解决"连不连得上"。
- **Profile(Agent 配置)**:一个 Agent 的完整声明,含名称、描述、身份、供应商选用(名/模型/温度)、工具、技能、渠道、引导文件、运行参数等;解决"这个 Agent 怎么用"。
- **LLM 调用审计记录**:一次大模型调用的留痕,含会话标识、供应商、模型、token 用量、耗时、成功标识、失败原因、起止时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 双供应商并存场景下,按名路由准确率 100%——自动化测试断言另一家模型零调用,无串台。
- **SC-002**: 引用未知供应商名的 Profile 在加载与调用两个环节均给出指明该名字的报错,报错定位耗时为零(无需翻日志猜原因)。
- **SC-003**: 失败的大模型调用 100% 留有审计记录(成功标识=false + 失败原因),与成功调用留痕率一致。
- **SC-004**: 核心验收测试套件不依赖真实网络与真实密钥,本地秒级跑完且全绿;真实连通性由手动冒烟(打标隔离)承担,外部服务可用性不影响流水线。
- **SC-005**: 更换某个 Agent 的模型只需改其 Profile 配置,上层调用代码零改动。

## Assumptions

- 核心阶段只接 OpenAI 兼容协议的供应商(如 DeepSeek、Kimi),其余供应商扩展阶段逐一接入并回归。
- 凭证一律走环境变量,配置文件中只允许 `${ENV_VAR}` 占位。
- 工程地基已就位:多模块构建、手工 schema 脚本机制、统一日志与异常体系(oryxos-init 已交付)。
- 这是第一节代码课,无前序节交付物;Profile 的其余字段校验规则(工具、渠道、引导文件存在性)由后续各节各自补充。
- fallback / hedge racing / 熔断 / 成本看板均明确推迟到扩展阶段。
