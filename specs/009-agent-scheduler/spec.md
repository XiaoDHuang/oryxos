# Feature Specification: 定时任务（第三种触发源）

**Feature Branch**: `025-lesson25-scheduler`

**Created**: 2026-09-05

**Status**: Draft

**Input**: 第25节需求：定时任务——让 Agent 不用人推一把，到点自己干活（钟推触发源，配置驱动、本地锁防重叠、失败照样审计、时区显式声明；仅随常驻模式注册）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置驱动的到点自动触发 (Priority: P1)

运维负责人在 Profile 里给"PR 日报 Agent"声明一条每天早上 9:00（显式时区）的定时规则，之后不再人工发消息：常驻模式（serve/gateway）启动时规则被注册进调度器，到点系统自动拼出规则里声明的消息，交给与人推（CLI/Web）完全相同的 Agent 处理入口跑完一次完整处理，结果可查。

**Why this priority**: 这是本特性的全部价值原点——"到点自己干活"。没有它，日报/周报/巡检类 Agent 不成立，31 节两个定时 Demo 没有地基。

**Independent Test**: 配一条"每分钟"规则启动常驻模式，到点观察到 Agent 自动发起一次处理，全程无人喂话；注册参数中可核验 cron 与时区均来自配置而非服务器默认。

**Acceptance Scenarios**:

1. **Given** 某 Profile 声明了含 id/cron/时区/消息四要素的定时规则，**When** 常驻模式启动，**Then** 该规则被注册进调度器，且注册参数同时携带配置的 cron 表达式与显式时区。
2. **Given** 规则已注册且到点，**When** 触发发生，**Then** 系统把规则声明的消息交给与人推完全相同的 Agent 处理入口，处理链路对消息来源零感知。
3. **Given** 交互式 chat 模式启动，**When** 上下文就绪，**Then** 不注册任何定时触发（用户决议，对齐技术方案 §8.6：定时任务随 serve/gateway 常驻调度）。
4. **Given** Profile 声明的规则缺少四要素之一或 cron/时区非法，**When** 常驻模式启动，**Then** 该条规则记错误日志并跳过，不阻断启动、不影响其他规则注册。

---

### User Story 2 - 重叠跳过与失败隔离 (Priority: P2)

某条规则上一次执行还没跑完，下一次触发点就到了——本次触发被直接跳过，不排队、不并行跑两份。另一次执行中模型调用报错——这次失败只记日志、照常落审计，调度器不崩，该任务后续触发照常进行，不会因锁未释放而永久卡死。

**Why this priority**: 没有它，P1 的主链路在长任务/故障场景下会叠加执行或整调度器瘫痪——是"敢不敢真挂到生产"的分水岭，但主链路本身已可独立演示价值。

**Independent Test**: 人为占住某任务的锁再触发一次，验证处理入口零调用；人为让处理入口抛异常连触发两次，验证异常不外抛且第二次仍能进入处理入口。

**Acceptance Scenarios**:

1. **Given** 任务 A 的上一次执行仍持有锁，**When** 任务 A 的下一触发点到达，**Then** 本次触发直接跳过，Agent 处理入口未被调用，跳过有日志。
2. **Given** 任务 A 执行中处理入口抛异常，**When** 本次执行结束，**Then** 异常不外抛、只记日志，调度器与其他任务不受影响。
3. **Given** 任务 A 上一次执行以异常结束，**When** 下一触发点到达，**Then** 任务 A 仍能正常进入处理入口（锁已释放，无永久卡死）。
4. **Given** 任务 A 某次执行失败，**When** 查询审计，**Then** 该次调用的 LLM/工具审计记录与人推触发的失败记账方式完全一致。

---

### User Story 3 - 定时触发的会话身份与历史连续性 (Priority: P3)

同一个 Profile 的历次定时触发落进同一个 Session（channel 与 user 固定为 "scheduler"），对话历史自然累积、由既有截断配置兜底——Agent 能"记得"昨天那次日报跑过什么，且审计视角下钟推与人推无二致。

**Why this priority**: 复用既有三元组会话机制、不新概念，是契约正确性收尾；价值真实但较前两个故事更偏内部一致性。

**Independent Test**: 同一 Profile 连续触发两次定时任务，核验两次落在同一个 Session 上，且身份三元组恒为 ("scheduler","scheduler",profileName)。

**Acceptance Scenarios**:

1. **Given** Profile P 的定时规则触发两次，**When** 取会话，**Then** 两次拿到同一个 Session。
2. **Given** 任意 Profile 的定时触发，**When** 会话被创建，**Then** channel 与 user 均固定为 "scheduler"，会话 id 沿用既有 channel+user+profile 联合生成公式。
3. **Given** 定时会话历史累积超过既有截断配置，**When** 再次触发，**Then** 历史按既有 max_history_turns 规则截断，不引入钟推专属概念。

---

### Edge Cases

- Profile 未声明任何定时规则（或 schedules 为空）：常驻模式正常启动，零任务注册。
- 多个 Profile 各自声明规则：全部注册，按任务 id 各自持锁，互不影响。
- 触发时长超过调度间隔：按 US2 跳过，不堆积。
- cron 表达式非法或时区标识无法识别：该条规则记错误日志并跳过，不阻断启动与其他规则（对齐既有 Profile 校验失败的处置哲学）。
- 规则 id 全实例唯一：任何重复（同一 Profile 内或跨 Profile）后者记错误日志并跳过注册——锁按规则 id 维度持有，id 冲突会导致不同任务互相阻塞，必须以唯一性约束根除。
- 规则变更（改 cron/时区/消息）：重启后生效，不支持运行时增删（扩展阶段能力）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 用户 MUST 能在 Profile 配置中声明定时规则列表，每条规则包含四个要素：规则 id、cron 表达式、显式时区、到点要发给 Agent 的消息；修改规则 MUST 只需改配置，不需改代码、不需重新编译。
- **FR-002**: 常驻运行模式（serve/gateway）启动时 MUST 扫描全部已注册 Profile 的定时规则并逐条注册进调度器；交互式 chat 模式 MUST NOT 注册定时触发（用户已决议，对齐技术方案 §8.6）。
- **FR-003**: 注册每条规则时 MUST 将配置的 cron 表达式与显式时区一并传入调度触发器，MUST NOT 依赖服务器系统默认时区。
- **FR-004**: 到点触发时系统 MUST 以固定身份（channel="scheduler"、user="scheduler"、对应 Profile 名）获取或创建 Session，并把规则声明的消息交给与人推（CLI/Web）完全相同的 Agent 处理入口；处理链路 MUST NOT 感知消息来自钟推。
- **FR-005**: 同一任务上一次执行未结束时，本次触发 MUST 直接跳过，不排队、不并行执行两份；防重叠 MUST 只用进程内按任务 id 维度的本地锁，MUST NOT 引入分布式锁或选主机制。
- **FR-006**: 单次执行失败 MUST 只记日志，不拖崩调度器、不影响其他任务的下一次触发；无论执行成败，任务锁 MUST 被释放；失败的调用 MUST 照常走既有 llm_calls/tool_invocations 审计路径，与人推触发的失败记账无差别。
- **FR-007**: 同一 Profile 的历次定时触发 MUST 复用同一个 Session（沿用既有三元组幂等公式），对话历史 MUST 由既有 max_history_turns 截断机制兜底，MUST NOT 为钟推新设会话概念。
- **FR-008**: 要素缺失、cron 非法、时区不可识别或规则 id 与已注册规则重复的规则 MUST 记错误日志并跳过注册，MUST NOT 阻断进程启动或其他规则的注册。

### Key Entities

- **定时规则（Schedule）**：Profile 上的一条声明式配置，四要素：规则 id（锁与日志的身份）、cron 表达式（何时触发）、时区（按谁的"早上 9 点"理解 cron）、消息（到点说什么）。改规则只改 Profile 配置。
- **Profile**：本特性为其 schedules 字段赋予完整运行时语义（此前仅作配置透传），其余字段不变。
- **定时触发**：一次到点执行，关联规则 id 与固定身份的 Session；其 LLM/工具调用进入既有审计表，无专属数据结构。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 配置一条"每分钟"规则后，常驻模式下到点 1 个周期间隔内 Agent 自动完成一次处理，全程 0 次人工发消息。
- **SC-002**: 100% 的定时触发执行（无论成败）都能在既有审计记录中查到账，与人推触发同一口径。
- **SC-003**: 任务执行时长超过调度间隔时，并发叠加执行次数为 0，且每次跳过都有日志可查。
- **SC-004**: 单次执行抛异常后，该任务后续触发的可执行率保持 100%（无锁泄漏导致的永久卡死）。
- **SC-005**: 变更规则的 cron/时区/消息内容只需编辑 Profile 配置并重启：0 行代码改动、0 次重新编译。
- **SC-006**: 交互式 chat 会话期间，定时触发注册数为 0；常驻模式启动时合法规则注册率为 100%。

## Assumptions

- 核心阶段为单实例部署，进程内本地锁足以防重叠；多实例协调属扩展阶段。
- cron 表达式采用运行平台调度器支持的格式（含秒的六段式）；用户写错格式按 FR-008 处置。
- 定时规则随进程启动注册，改动需重启生效；运行时增删规则的接口属扩展阶段，本特性不做。
- Profile 的 schedules 字段此前已作为配置契约存在（透传形态），本特性把它落成四要素规则并接入调度，不改变其他字段语义。
- "仅常驻模式注册"通过启动信号区分（用户决议的接线方式），不需要运行时开关。
- 定时任务失败的告警与自动重试不做；核心阶段目标为"失败不崩、留痕可查"。
