# Feature Specification: 可切换的三后端长期记忆

**Feature Branch**: `codex/007-memory-backends`

**Created**: 2026-08-30

**Status**: Done — 2026-09-04 归档。85/85 任务完成，R1–R5 全通过；各故事提交见 acceptance.md；Mem0 后端默认关闭，生产启用仍需企业获准环境与部署人员注入 Secret。

**Input**: User description: "在已归档的 006 文件式 Memory 基线上，采用已批准的方案 B：默认 Markdown、可选 SQLite 和企业自托管 Mem0，保持现有记忆使用方式与运行时契约，先同步治理再推进 007 的正式规格。"

## Clarifications

### Session 2026-08-30

- Q: 007 的 Mem0 是否按原文保存与语义检索交付，不启用自动提炼、合并或替换归档内容？ → A: 否，启用自动提炼、合并和替换归档内容；限 Mem0 显式保存归档时的后端处理，核心记忆仍保持原文完整，既有数据边界和审计门禁不变。
- Q: 是否保留原始输入及被合并、替换的旧归档作为可追溯历史，但不让它们参与常规召回？ → A: 是，保留原始输入和被合并、替换的旧归档供审计与排查；常规召回及自动上下文只使用当前有效事实，不混入历史版本。

## User Scenarios & Testing *(mandatory)*

故事编号沿用已批准的 007 拆解。P1/P2 表示优先级，不代表 P2 可以从本特性交付中省略；US4 的共同验收随 US1–US3 一起建立，最终验证三种后端。

### User Story 1 - 不改配置，继续使用已有记忆 (Priority: P1)

作为已经使用 OryxOS 的用户，我希望升级后仍能通过原来的保存、回忆与对话方式使用已有记忆，不需要部署新的记忆服务、重新录入偏好或修改现有 Agent 配置。

**Why this priority**: 006 已建立可用的文件式记忆；新增选择不能让现有用户承担迁移成本或丢失历史。

**Independent Test**: 使用包含核心和归档内容的 006 工作区，不设置新的后端选择，也不提供远端凭证；完成读取、保存、新会话和重启，确认历史保留、下一轮可见且没有外部记忆服务访问。

**Acceptance Scenarios**:

1. **Given** 用户已有合法的文件式记忆且没有选择后端，**When** 启动并开始对话，**Then** 默认仍使用 Markdown，原有核心内容完整可用，且不要求任何远端记忆服务或凭证。
2. **Given** 用户通过已有记忆工具保存内容但未指定范围，**When** 保存成功并进入下一轮，**Then** 内容归入归档并按既有窗口规则可用；显式选择核心时，原文完整出现在核心记忆中。
3. **Given** 归档内容处于 3999、4000、4001 个既有字符计数单位的边界，**When** 构建下一轮上下文，**Then** 最多带入最近 4000 个单位，核心内容不变，未带入的旧归档仍能按关键词找回。
4. **Given** 工作区包含 006 已支持的旧格式或缺失分区，**When** 读取或保存，**Then** 沿用既有兼容行为，不丢合法内容、不将核心当作归档裁剪，也不修改用户维护的初始偏好资产。
5. **Given** 本地后端已选中，**When** 启动、保存、回忆或构建上下文，**Then** 未选后端没有记忆数据访问、远端探活或凭证要求。

### User Story 2 - 在本地结构化保存和找回记忆 (Priority: P1)

作为部署管理员，我希望选择 SQLite 长期记忆，让同一工作区的 Agent 在无需外部记忆服务的条件下保存更多条目，并以明确的规则注入最近归档和查找历史。

**Why this priority**: 这是保留本地部署体验的另一种存储选择；必须先保证数据可靠和查询含义清楚。

**Independent Test**: 在独立工作区选择 SQLite，保存核心内容和超过 100 条的归档；检查下一轮上下文、新会话及重启后的结果，并检索不在最近 100 条中的历史条目。

**Acceptance Scenarios**:

1. **Given** 管理员选择 SQLite 且目标没有长期记忆，**When** 分别保存核心和归档并重启，**Then** 两类已确认保存的原文均可恢复，核心完整进入下一轮上下文。
2. **Given** 归档分别有 99、100、101 条，**When** 构建上下文，**Then** 核心始终全量，归档最多选最近 100 条并按保存顺序稳定展示，较早归档不被删除。
3. **Given** 核心与旧归档包含相同关键词，另有包含 `%`、`_`、大小写差异和中文的归档，**When** 按字面关键词回忆，**Then** 只返回大小写保持的包含匹配归档，特殊字符没有额外查询含义；不在注入窗口中的匹配归档仍可找到。
4. **Given** 工作区已有会话和审计历史，**When** 首次启用本地结构化记忆并重复启动，**Then** 既有会话及审计记录保持不变，不重复初始化或覆盖已保存记忆。
5. **Given** 同一运行实例内多次保存接近同时发生，**When** 这些保存均返回成功，**Then** 每项确认的保存均保留，不因并发互相覆盖。

### User Story 3 - 显式使用受控的自托管记忆服务 (Priority: P2)

作为企业部署管理员，我希望在确认数据始终留在批准环境内后，显式选择自托管 Mem0；Agent 继续使用原来的记忆工具，显式保存归档时由后端自动提炼事实、合并重复内容并替换过时内容，后续能用意思相近的表达找回当前有效归档。服务不可用或安全条件不满足时，我需要明确失败，而不是误以为记忆为空或已经保存。

**Why this priority**: 服务化记忆与语义召回增加部署及数据流转成本，只有在默认兼容和安全条件明确后才适合交付。

**Independent Test**: 在隔离、获准的自托管环境中保存核心及包含冗余、重复和更新事实的归档输入，验证核心原文不变、归档被提炼/合并/替换且当前有效事实可用同义表达找回；再分别模拟未授权目标、凭证缺失、服务失败和处理延迟，验证拒绝、超时、结果完整性和不降级行为。

**Acceptance Scenarios**:

1. **Given** 自托管服务及其下游数据路径均已获准，且管理员明确选择该服务，**When** 保存核心与归档，**Then** 核心原文完整保留；归档自动处理后的有效记忆状态已持久化，只有确认下一轮可读取该状态时才报告保存成功，不要求归档输入逐字成为当前条目。
2. **Given** 归档记录“项目部署在 K8s 集群”，核心区也存在相似信息，**When** 用“项目的 Kubernetes 部署环境”回忆，**Then** 可找回预先指定的相关归档，不返回核心条目；不要求结果与字面关键词匹配完全相同。
3. **Given** 核心记忆总量超过服务一次能返回的数量，**When** 构建上下文，**Then** 所有核心原文仍完整可用，不因一次返回数量限制而静默遗漏；归档按有界窗口注入而非无限加入。
4. **Given** 任一必需凭证、安全检查或数据路径批准缺失，或访问目标在请求过程中改变为未获准位置，**When** 尝试访问记忆服务，**Then** 在向不合规目标传输记忆前拒绝请求，不用默认云服务补位。
5. **Given** 保存处理延迟超过管理员设定的等待上限，或服务返回拒绝、故障、无效或不完整结果，**When** 本次操作结束，**Then** 返回明确失败或结果不确定的说明，不报告保存成功、不将读取错误包装成“没有找到相关记忆”，也不切回本地后端。
6. **Given** 两个工作区使用同一自托管服务，**When** 分别保存和检索，**Then** 工作区之间不串数据；同一工作区内更换会话或 Agent 配置仍能使用该工作区共享记忆。
7. **Given** Mem0 归档已记录“项目使用 Java 17”，**When** 显式保存“项目已升级到 Java 21”以及重复描述该新事实的输入，**Then** 当前有效归档反映 Java 21，旧值不再作为当前事实召回，重复事实可以合并；核心区若有同名信息仍保持原文，不被跨范围更新。
8. **Given** 显式归档输入包含事实及冗余描述，**When** 后端执行自动提炼，**Then** 验收样例中的目标事实被准确保留为有效归档，不要求逐字复制冗余描述；处理结果与本次保存操作可关联。
9. **Given** 归档经过一次提炼、重复合并和过时事实替换，**When** 重启后核对历史与常规召回，**Then** 能追溯每次原始输入、被合并或替换的旧内容及对应有效结果；常规召回和自动注入的归档只来自当前有效条目，不从历史记录加载原始输入副本或失效旧版本，核心注入规则不变。
10. **Given** 归档处理无法保证原始输入或旧版本的持久留存，**When** 尝试合并或替换，**Then** 不得将未保全的旧内容不可恢复地覆盖；本次操作明确失败或说明结果不确定，不虚报完整成功。

### User Story 4 - 知道切换结果，并能追溯每次记忆操作 (Priority: P1)

作为管理员和使用者，我希望清楚知道当前使用哪个后端、切换后能看到哪些数据，并能追溯保存与回忆的成败，避免“换后端等于自动搬数据”的误解。

**Why this priority**: 数据保留、明确失败和审计是每一种后端都必须满足的安全底线，而不是交付后补充的说明。

**Independent Test**: 先用已有两个本地后端验证“保存 → 切换 → 保存 → 回切”及审计；自托管后端可用后执行同一组场景。每个后端均可独立验证，不依赖另一个后端的查询结果证明自身正确。

**Acceptance Scenarios**:

1. **Given** 后端 A 已保存记忆、后端 B 为空，**When** 管理员改选 B 并重启，**Then** 系统使用 B 的独立数据，说明没有迁移旧数据；A 的记忆不被搬运、删除或双写，回切 A 后仍可读取。
2. **Given** 系统正使用后端 A，**When** 管理员只修改选择但未重启，**Then** 当前运行实例不热切换；重启后才采用新的合法选择。
3. **Given** 管理员填写不支持的后端或选中不可用后端，**When** 启动需要长期记忆的运行时，**Then** 得到可定位到配置项或依赖的错误，不静默选用其他后端，也不影响不需要记忆的既有轻量命令。
4. **Given** Agent 获准使用记忆工具，**When** 保存或回忆成功、失败或超时，**Then** 现有审计链路记录实际结果；审计自身失败也能被发现，错误消息不泄漏凭证。
5. **Given** 核心记忆、归档和超过历史上限的会话均存在，**When** 分别使用三种后端构建上下文，**Then** 身份与初始设定、长期记忆、最近会话的既有相对顺序不变，会话角色与最近历史上限不变。
6. **Given** 管理员准备启用或切换后端，**When** 查阅使用说明，**Then** 能确认默认项、当前选择的判定方式、重启生效、数据位置与保留、检索差异、Mem0 归档会自动提炼/合并/替换、历史仅用于追溯而不参与常规召回、等待上限及失败处理，不需要新增管理界面。

### Edge Cases

- 未选择后端、非法选择、选中后端参数缺失，与未选后端参数缺失必须区分；只有选中后端的必需条件参与记忆就绪判定。
- 缺失工作区时给出明确错误，不在其他位置悄悄创建记忆；合法空后端可报告无记忆，但访问失败不能报告为空。
- 内容或查询为空白、范围非法时拒绝操作；未提供范围才使用归档默认值，不能用默认值掩盖非法输入。
- 核心记忆很大或归档超出窗口时，不得为缩短上下文而删除或改写核心；若完整上下文无法被处理，应明确失败。
- 字符边界、多行及 Unicode 内容沿用 006 计数口径，不在升级时改变原有裁剪结果；本地结构化后端使用条目数量而不是字符预算。
- 相同保存时间的多条归档必须有稳定先后；窗口外仍有效的归档不应被窗口规则排除出查询。Mem0 被合并或替换的旧版本持久保留用于追溯，不作为当前有效事实召回或自动注入上下文。
- 服务只返回部分数据、重复数据或不完整结果时，不得把不完整核心冒充完整上下文。
- 保存已可能生效但响应丢失时，不得盲目重试造成重复副作用；说明结果不确定，并由后续计划确定可验证的恢复规则。
- 原文没有发生新保存时，结束会话、上下文增长、重启或更换 Agent 配置均不得触发自动记忆提炼。
- Mem0 的提炼、合并和替换只作用于显式保存所触发的归档处理，不得修改核心、其他工作区或未选后端；已明确执行的合并/替换不应被误判为并发写入丢失。
- 重复输入经合并后，有效事实数量可以不增加，但本次原始输入与处理结果仍须可追溯；不能仅按条目数是否增长判断保存成功。
- 原始输入或旧版本留存失败时不得虚报完整成功，也不得永久覆盖尚未保全的旧内容；留存历史同样受工作区隔离、凭证保护和数据不出域约束。
- 历史记录与当前有效条目可能文本相同；排除规则依据其历史/有效身份，不能因文本相同误删有效归档，也不能据此改写或裁剪核心记忆。
- 远端协议超出请求/响应限额或合法提炼没有新增事实时，要明确区分拒绝、已处理无需更新和结果未知；不能用统一“新增成功”文案误导。远端限额不改变本地原文后端的既有能力。
- 一份当前快照同时服务核心和归档读取，分页游标不得跨分区/快照复用；两类身份不能混为同一个scope绑定。
- 保存已派发但响应失真、身份不符或没有可信终态时，即使收到HTTP响应也须查询原操作；仍未确认就报告结果未知，不能把协议错误当作确定未保存。
- 模型生成结果须在提交前满足条目和实际序列化响应预算。召回可因预算只返回排序后的完整前缀并保留可观察标记，不截断正文；有匹配却无法容纳完整条目时不得伪装无匹配。
- 不同工作区共享服务时必须隔离；同一工作区切换用户或 Agent 配置不改变既有长期记忆共享范围。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供 Markdown（默认）、SQLite、自托管 Mem0 三种长期记忆选择；未设置选择时保持 006 的使用体验，不要求新增外部服务。
- **FR-002**: 每个运行实例 MUST 在启动时唯一确定后端，重启后才应用选择变更；非法或不可用的选择 MUST 明确失败，MUST NOT 静默降级。
- **FR-003**: 系统 MUST 不访问未选后端的记忆数据、不发起其网络连接或探活，也不要求其凭证；无需记忆的既有轻量操作不受远端条件影响。
- **FR-004**: 系统 MUST 兼容 006 的已有合法文件、旧格式处理和使用入口，保留原内容且不改写用户维护的初始偏好资产。
- **FR-005**: 系统 MUST 保持当前工作区内跨会话、跨 Agent 配置共享长期记忆的含义；不同工作区 MUST 不因共用服务而相互读取或修改记忆。
- **FR-006**: 长期记忆 MUST 区分核心与归档并记录保存时间；只有显式保存才能触发新增或更新记忆，范围省略时为归档，非法范围必须拒绝。Mem0 归档允许将一次输入提炼为事实，合并重复内容并替换过时事实，本地后端仍保存原文。
- **FR-007**: 每轮上下文 MUST 包含全部核心原文，核心内容不得被裁剪、合并、推理改写或加入归档搜索结果；无法完整取得时明确失败。
- **FR-008**: Markdown MUST 沿用 006 的最近 4000 个字符计数单位的归档注入规则；SQLite MUST 注入最近 100 条归档；Mem0 MUST 对当前有效归档使用有说明、有边界的窗口。窗口裁剪只限制上下文，不删除数据；Mem0 的归档合并/替换属于 FR-022 的独立处理，不由窗口裁剪触发。
- **FR-009**: 两种本地后端 MUST 对全部归档做大小写保持的字面包含匹配，按稳定的保存先后返回；查询字符不得被解释成通配表达式，核心区不得混入。
- **FR-010**: 自托管后端 MUST 支持经验收的语义归档召回，对事先确认的同义表达场景找回指定的当前有效归档，并排除核心、其他工作区以及已失效的旧事实；不承诺与关键词检索相同的命中集合或排序。
- **FR-011**: 保存成功 MUST 表示本地后端与核心原文、或 Mem0 归档处理后的有效记忆状态已持久化且可读，下一轮可按范围和窗口规则使用；服务若延迟处理，必须在有限等待内确认，否则明确失败或结果不确定。Mem0还 MUST 完成FR-022历史留存及生成结果/成功响应的提交前预算校验；确认对象是有效结果和历史，不是输入逐字成为当前条目。
- **FR-012**: 核心内容 MUST 在成功保存后的每轮完整可用；归档查询只需返回符合该后端查询规则的内容。系统 MUST NOT 将“可读”错误解释为“任何查询都必须命中”或“超出窗口的归档也必须全部注入”。
- **FR-013**: 同一工作区在新会话和正常重启后 MUST 能恢复本地后端与核心原文，以及 Mem0 已确认的当前有效归档状态和可追溯历史；同一实例的并发成功保存不得发生非预期覆盖或丢失。Mem0 已明确执行、历史得到保留且可关联到保存操作的提炼、合并和替换不属于非预期丢失。
- **FR-014**: 首次启用及后续升级本地结构化记忆 MUST 保留原会话、审计和已保存的记忆；重复启动不得重复初始化或破坏历史。
- **FR-015**: 系统 MUST 沿用既有的保存/回忆工具名称、输入含义、授权和统一执行入口；调用方无需了解具体存储；会话身份、最近历史上限、消息角色及上下文相对顺序不变。
- **FR-016**: 空白内容、空白查询、非法范围、缺失工作区、存储不可读写和无效返回 MUST 产生明确错误，不泄漏凭证或无关本地路径；正常的无匹配结果与操作失败 MUST 可以区分。Mem0远端正文、查询及模型生成内容含U+0000时 MUST 在登记/出站/提交前拒绝，不得删除、替换或编码改写后虚报原文保全；hash字段间NUL分隔符及本地后端输入能力不变。
- **FR-017**: 切换后端 MUST 只改变重启后的访问目标；MUST NOT 自动搬运、双写、删除或清空任何旧后端数据。切换到空目标必须说明没有迁移，回切可恢复旧数据视图。
- **FR-018**: Mem0 MUST 默认关闭，仅允许管理员明确选择的企业自托管环境；每次出站前必须验证目标获准，缺少安全控制或目标变为不合规时，必须在传输记忆前拒绝。
- **FR-019**: 启用自托管后端前 MUST 验证服务及其模型、向量化处理和存储下游都在批准数据域内；仅入口自托管不足以放行。不得默认遥测或将记忆发往未批准服务。
- **FR-020**: 凭证 MUST 由安全注入方式提供，不能明文写入代码、持久配置、错误或审计消息；缺少选中后端必需凭证时不得开始记忆访问。
- **FR-021**: 服务超时、拒绝、不完整读取和未知保存结果 MUST 可观测，不得包装成成功或无记忆。保存请求派发后，仅可信且匹配的持久终态能确认结果；响应失真/身份不符/错误或查询失败不能当作确定未提交，须查询原操作或报告未知。自动重试不得产生重复副作用。
- **FR-022**: 在自托管部署及数据/审计门禁满足后，Mem0 MUST 在显式保存归档时启用自动提炼、合并和替换；当前归档呈现处理后的有效事实，MUST NOT 改写 FR-007 的核心原文，也不得新增启动、会话结束或上下文压力触发器。每次原始输入与被合并/替换的旧归档内容 MUST 持久保留，可关联到工作区、本次保存、处理结果及先后关系，供审计和排查；不得因合并、替换或窗口裁剪而永久删除这些历史。常规召回和自动归档注入 MUST 只读取当前有效条目，不从历史记录读取原始输入副本或失效旧版本；文本相同的有效条目不因此被排除。历史未保全时不得不可恢复地覆盖旧内容或虚报成功；若所选服务不能满足处理与留存要求，应报告准入不满足，不得静默退回不提炼或不留历史模式。
- **FR-023**: 经现有工具链发生的保存与回忆 MUST 按实际成功、失败或超时结果留存审计；审计写入故障不得静默。服务内部模型处理必须有独立可验证的审计来源与关联，不能把工具审计冒充完整的内部处理记录。
- **FR-024**: 用户说明 MUST 明确默认后端、选择与生效时机、各后端保存/查询/窗口差异、Mem0 归档自动提炼/合并/替换及其结果含义、切换不迁移、数据保留、服务等待上限和故障处理；不得宣称未通过真实环境验收的后端已经可用。

### Scope Boundaries

- 本特性在 006 之上增加可替换的长期后端，不重写其归档规格和验收记录，也不将旧证据算作新后端完成证据。
- 本特性不新增启动、会话结束或上下文压力触发的自动提炼，不做情景记忆、Memory Wiki、知识图谱、自建向量检索系统、独立记忆压缩任务、内容缓存、热切换、自动迁移、多租户治理或新的管理界面。已批准的 Mem0 显式保存内归档提炼/合并/替换不属于上述排除项。
- Mem0 作为可选记忆服务，不接管 Agent 的推理循环、工具执行或会话管理；外部 Agent 运行时集成不在范围内。
- 维持已批准的现有架构和公共契约。实现层的接口落位、数据结构、第三方协议及安全装配由 plan 按宪法核验，不在此规格中重新设计。
- 保留可追溯历史不等于新增面向 Agent 的历史检索工具、管理界面、回滚功能或自动清理任务；007 验收通过受控核对证明历史存在及关联正确，具体历史落位在 plan 确定。
- 用户已批准追加受控 Mem0 服务端适配及所需 HTTP 白名单接线，用于兑现上述契约；仍保持 9 个 Maven 模块，不增加 Agent runtime 或完整 Sandbox。实际部署启用仍须通过数据、安全和验收门禁。

### Key Entities

- **后端选择**: 管理员指定的长期记忆保存位置与访问方式；一次运行仅有一个生效选择，变更需重启。
- **长期记忆条目**: 本地后端及核心保存原文；Mem0 归档保存经显式调用触发处理后的有效事实，具有范围、保存或变更时间及稳定先后关系。不得混淆当前有效条目与已合并/替换旧版本，也不得混淆核心和归档。
- **归档变更历史**: Mem0 每次显式保存的原始输入、被合并或替换的旧内容，以及与处理结果、工作区、本次保存和先后关系的关联；持久保留供追溯，不是可直接召回的有效记忆。
- **工作区记忆边界**: 本特性沿用的长期共享范围；同一工作区的会话和 Agent 配置共享记忆，不同工作区互相隔离。
- **本轮记忆上下文**: 全部核心、后端规定的归档窗口与当前会话最近历史；窗口不是数据删除策略。
- **记忆操作结果与证据**: 保存或回忆的成功、无匹配、失败或不确定结果，以及可追溯的操作与服务处理记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 既有工作区在不增加后端配置、不部署远端服务的条件下，100% 完成“读取旧偏好 → 保存新内容 → 新会话/重启 → 再次使用”的默认流程，历史内容损失为 0。
- **SC-002**: 三种后端各自的验收中，100% 已报告成功的保存均在下一轮按范围和窗口规则可用；核心原文遗漏或改写为 0。正常重启后，本地/核心原文及 Mem0 已确认的有效归档状态与变更历史均可恢复，不将留有历史的已确认归档提炼、合并或替换误判为数据丢失。
- **SC-003**: 所有归档窗口边界用例都保留完整核心及规定的近期有效归档，窗口外仍有效的归档可查询，因窗口裁剪导致的持久数据删除为 0。
- **SC-004**: 字面检索场景的预期命中/未命中逐项一致；语义检索场景逐项找回事先指定的当前有效归档。提炼、重复合并和过时事实替换用例均得到预期有效事实；归档检索混入核心、其他工作区的次数为 0，常规召回及自动归档注入从历史记录取入原始输入副本或失效旧版本的次数为 0。
- **SC-005**: 覆盖三种后端之间全部 6 个有向切换组合：目标独立、重启生效、旧数据保留、回切恢复均通过；隐式搬运、双写、清空或降级次数为 0。
- **SC-006**: 未选后端产生的数据访问、网络连接和凭证要求均为 0；缺少安全批准或凭证的出站拒绝用例中，发送到不合规目标的记忆内容为 0。
- **SC-007**: 所有无效输入、访问拒绝、超时及部分结果用例均明确区分失败与无匹配；等待不无限持续；虚报成功、把未确认保存判为确定未提交、泄漏凭证或重试重复保存均为0。生成结果超预算在提交前拒绝，召回预算缩减不截正文或伪装空结果。
- **SC-008**: 每种后端的保存、回忆及失败场景均能找到实际结果的审计证据；Mem0 提炼、合并、替换验收中，100% 已确认处理均可追溯原始输入、涉及的旧归档及有效结果。历史留存和审计故障可以被识别，不以日志或工具结果冒充不存在的内部处理记录。
- **SC-009**: 前序对话、授权、会话历史顺序与用户维护资产的回归场景全部保持通过；管理员能仅凭使用说明完成“选择 → 重启 → 验证 → 回切”，无需重新定义 Agent 或记忆工具。

## Assumptions

- 依据为 [需求 §5.5](../../docs/DemandAnalysis.md)、[技术方案 §5/§9/§10](../../docs/TechnicalSolution.md)、[007 批准范围](../../docs/decisions/007-memory-backends-scope.md) 和 [宪法 v3.0.0](../../.specify/memory/constitution.md)。技术决策仍受这些文件约束，此规格只定义行为与验收。
- 006 归档提交 `3d60ee0` 是兼容基线；007 的三后端、安全和审计证据需要独立取得；当前实现与已验证范围以tasks/acceptance台账为准，尚未整体通过。
- 用户在本次 clarify 中明确批准 Mem0 归档启用自动提炼、合并和替换，并保留原始输入及被合并/替换的旧版本作为可追溯历史，取代先前的原文保存默认。该决定仅覆盖显式保存所触发的归档处理，不批准核心改写、额外自动触发器、历史自动删除或未核验的数据外发。
- 字符预算沿用 006 的既有计数口径，不改变 Unicode/多行边界行为；具体映射在 plan 固化。服务归档窗口的数量、稳定排序和等待上限按已批准范围由 plan 核验并写入使用契约，不假定等同于任一本地后端。
- 研究已确认原版Mem0不能直接满足本规格；用户批准采用受控外部适配，开发基线和自有协议已在plan固定。真实组合兼容性、事务/故障行为、完整数据路径和审计能力仍待实施验收；不能把设计要求当作第三方现成功能或放宽断言。
- 服务化后端的最终验收依赖获准的真实自托管测试环境。受控替身可以验证异常行为，但不能代替真实环境的最终适配验收；缺少环境时不得声明 007 全部完成。
- 现有工作区初始化、会话存储、工具授权与审计能力可复用；不新增租户/用户级隔离或独立 Session 模型。
